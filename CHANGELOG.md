# Changelog

All notable changes to `@coodra/cli` are recorded here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Beta tags do not guarantee SemVer; breaking changes between `0.2.0-beta.x` releases are possible and called out per entry.

## [Unreleased]

### Fixed

- **2026-07-30 — COOD-7 review follow-ups: fixed a wrong `GRAPHIFY_OUT` value in the bundled skill, and rewrote doctor check 28 to verify the native Claude Code plugin instead of the retired HTTP-bridge hook model.** (1) The `coodra-graphify` skill bundled into both the Claude and Codex plugins told the agent to set `GRAPHIFY_OUT=.coodra/graphify` — missing the `/out` suffix, so it pointed at a different directory than `MANAGED_OUT_REL` (`.coodra/graphify/out` in `packages/cli/src/lib/graphify/artifacts.ts`), the path Coodra's own Graphify command actually reads from. Fixed in both `claude-plugin.ts` and `codex-plugin.ts`. (2) Doctor check 28 (`28-claude-hook-registration.ts`) still parsed `~/.claude/settings.json`'s `hooks` key for HTTP-type entries pointing at the hooks bridge (`http://<host>:<port>/v1/hooks/claude-code`) — the pre-plugin-migration integration model. `coodra agent add claude` hasn't written that key in months; hooks now live inside the plugin's own `hooks/hooks.json` as `mcp_tool`-type entries calling `plugin:coodra:coodra` → `lifecycle_event` directly. Left alone, the check would report every correctly-installed native plugin as "missing hook registrations" forever. Rewrote it to delegate to `probeClaudePlugin` (the same probe `coodra agent status` uses) instead of re-parsing settings.json by hand, so the two surfaces can't drift apart again; it reports which specific plugin surface is missing (enablement / marketplace registration / manifest / MCP / hooks / skills) rather than a flat pass/fail. Gave `probeClaudePlugin`'s CLI-based check (`claude plugin list --json`) a short, injectable timeout for this use (`createClaudeCliRunner(1200)`, replacing the single `defaultClaudeCliRunner` export with a factory) — doctor's default per-check budget is ~2s, well under the 15s timeout appropriate for an actual install, so a slow/hung CLI call now fails fast and falls back to the file-based checks instead of the whole check racing past doctor's own timeout and reporting an uninformative "timeout" status. While rewriting the check's tests, found and fixed a second, unrelated pre-existing bug: `AgentPathContext.settingsPath` (documented as a test-override field) was never actually read anywhere in `claude-plugin.ts` — `claudePluginPaths` always recomputed `~/.claude/settings.json` from `userHome`, silently ignoring the override on both the read side (`probeClaudePlugin`) and the write side (`installClaudePlugin`/`removeClaudePlugin`). `claudePluginPaths` now takes the override as an explicit third parameter, threaded through from all three call sites.

- **2026-07-30 — The hand-written Claude Code cache-mirror fallback now prunes its own stale versions instead of leaking a directory on every release.** Follow-up to the entry below, after investigation showed the `claude plugin` CLI path only ever engages for users who separately installed the standalone CLI — the Desktop app (code.claude.com/docs/en/desktop-quickstart: "The desktop app includes Claude Code. You don't need to install Node.js or the CLI separately") bundles its own engine and never puts `claude` on `PATH`, so for Desktop-only users `installClaudePlugin` always takes the hand-written fallback, not the CLI path. That makes the fallback's own correctness the actually load-bearing concern, not a secondary one. Investigated `CLAUDE_CODE_PLUGIN_SEED_DIR` as a candidate replacement for the fallback and ruled it out: it doesn't appear in the general env-vars reference (code.claude.com/docs/en/env-vars) at all — only in the container/CI section of the plugin-marketplaces guide — so there's no basis to assume it's settable via `settings.json`'s `env` key the way documented runtime variables are; and separately, the desktop docs state plainly that "the desktop app does not always inherit your full shell environment... on macOS... it reads your shell profile to extract PATH and a fixed set of Claude Code variables, but other variables you export there are not picked up" — so even a working env-var mechanism likely wouldn't reach Desktop sessions. Conclusion: direct file writes into the shared `~/.claude/` tree (what the original code already did) are the correct, working mechanism for both CLI and Desktop-local sessions; hardening means fixing the write itself, not replacing it. `installClaudePlugin`'s fallback branch now calls `pruneStaleCacheVersions` after writing the current version, which removes sibling version directories under `~/.claude/plugins/cache/coodra/coodra/` older than a 14-day grace window — mirroring Claude Code's own documented eviction window ("the previous version directory is marked as orphaned and removed automatically 14 days later. The grace period lets concurrent Claude Code sessions that already loaded the old version keep running without errors") rather than deleting immediately, so an in-flight session on the just-superseded version isn't broken. `removeClaudePlugin` now removes the entire `cache/coodra/coodra/` versions directory (not just the current version) on full uninstall, since there's no concurrent-session concern once the user has explicitly asked to remove everything. Out of scope, flagged not silently dropped: the Desktop app's separate **Cowork** tab sources plugins from a cloud-synced `claude.ai` account config, not `~/.claude/` at all (code.claude.com/docs/en/desktop: "The Cowork tab... sources its skills, plugins, and connectors from this Customize configuration, which syncs through your claude.ai account, not from the CLI's `~/.claude` directory") — neither this fix nor the CLI-preferred path reaches that surface; whether it needs to is an open product question.

- **2026-07-30 — Claude Code plugin install now prefers the documented `claude plugin` CLI over hand-writing Claude Code's plugin cache.** `installClaudePlugin` first tries `claude plugin marketplace add <marketplace-root>` + `claude plugin install coodra@coodra --scope user` when the `claude` binary is on `PATH`; Claude Code's own binary then owns `settings.json`, `known_marketplaces.json`, and the versioned plugin cache directly. Previously Coodra always hand-wrote a mirror of the plugin bundle directly into `~/.claude/plugins/cache/coodra/coodra/<version>/` — an undocumented directory shape reverse-engineered from observed Claude Code behavior, not a stable API. That write bypassed Claude Code's install/update-triggered cache-eviction bookkeeping (docs: "the previous version directory is marked as orphaned and removed automatically 14 days later" — code.claude.com/docs/en/plugins-reference), so every beta version bump left a permanent, uncollectable directory under the old version's cache path since no install/update *operation* was ever recorded for it. `removeClaudePlugin` mirrors this: it now attempts `claude plugin uninstall coodra@coodra --scope user` first, then always runs the existing manual cleanup afterward (idempotent, so it's safe regardless of CLI outcome) to remove the Coodra-owned marketplace source and legacy artifacts the CLI doesn't know about. `probeClaudePlugin` now also checks `claude plugin list --json` when the CLI is available, so `coodra agent status`/`doctor` don't report a CLI-installed plugin as "missing" just because Coodra's own cache mirror is absent. The hand-written settings/cache path from before is retained as the fallback for the common case where `claude` isn't on `PATH` yet (Coodra runs before Claude Code has ever been launched) — that fallback's own reliance on an unverified cache-directory shape is unchanged and tracked as a follow-up (candidate fix: `CLAUDE_CODE_PLUGIN_SEED_DIR`, documented for container/CI provisioning but not verified here against a cold Claude Code install — no `claude` binary was available in the environment this was written in to test it live). Known residual gap: `packages/cli/__tests__/integration/agent-command.test.ts` still exercises `installClaudePlugin`/`removeClaudePlugin` through the real `defaultClaudeCliRunner`, which shells out to the actual system `claude` binary if one is on the test runner's `PATH` — on such a machine the integration suite would mutate that machine's real `~/.claude/settings.json` with a plugin entry pointing at a temp directory. Low risk on typical CI (no `claude` binary expected there), but not eliminated; fixing it needs the fake-CLI injection seam (`ClaudeCliRunner`, already added in `claude-plugin.ts`) threaded through `resolveAgentWiringContext`/`adapters.ts`, which was left out of this change to keep the diff scoped to the cache-write fix.

## [0.2.0-beta.28] — 2026-07-24

Six phases of the stakeholder enhancement roadmap plus a whole-product QA sweep. Two user-facing renames (`coodra skill`, the three `*_skill*` MCP tools) ship with aliases so nothing existing breaks. Every phase was validated live on a real machine before the next one started.

### Added

- **`coodra agent add|status|remove|repair <agent>` — per-agent wiring as a first-class command group.** Wiring one coding agent used to mean re-running the whole `coodra init` and accepting whatever it detected; there was no way to add an agent later, repair a drifted config, or strip one agent without stripping all. The new Agent Registry (`packages/cli/src/lib/agents/`) accepts `claude | cursor | codex | windsurf | devin | all | detected`. `add` wires the bundle (project `.mcp.json` + the per-agent MCP config + the instruction contract), `repair` force-rewrites to heal drift, `remove` strips one agent's surfaces while leaving `.mcp.json`, and `status` reports per-file tri-state. `devin` is an input+display alias for `windsurf` (as are `cascade` / `codeium`); the DB `agent_type` stays `windsurf`. `init` is refactored onto the same registry, so its behaviour and the new command can't diverge.
- **`coodra files status|clean` + a project-local `.coodra/` folder.** Coodra scattered generated files across a repo with no record of what it had written, so cleanup was manual and guesswork. `.coodra/config.json` carries project identity, and `.coodra/manifest.json` is an ownership ledger: one `classifyGeneratedPath` maps every file to owner / kind / cleanup-tier / scope. `clean` is safe by default — it deletes only `safe` files, `ask` files need `--force` or a prompt, and `preserve` + `global` files are never touched. `doctor --fix` migrates legacy projects to `.coodra/config.json`.
- **`coodra graphify build|open|clean` + a `/graphify` page in the dashboard.** Graphify wiring existed but the artifacts were unmanaged: no pinned output location, no way to build or inspect a graph from Coodra, and nothing in the web app. Builds now land in a managed `.coodra/graphify/out` (recorded in `.coodra/graphify.json`), and the layout precedence — recorded choice, then an existing `graphify-out/`, then managed — is identical in `enable` and `resolveGraphifyPaths`, so a git-committed `graphify-out/` is never silently relocated. The new web section lists every project's graph status, renders the report, and embeds the interactive graph.
- **`coodra skill` command group (`add`, `list`, `show`, `edit`, `index`, `remove`, `migrate`).** The atomic pull-on-trigger knowledge units are now called **Skills**, matching the Anthropic Skills pattern they implement; Feature **Packs** (module blueprints) keep their name. `coodra feature` remains as a command alias, and `skill migrate` moves a legacy `docs/features/` directory to `docs/skills/` (simple rename, or a per-slug merge, refusing collisions without `--force`).
- **Deep Wiki grounding now includes the codebase graph and prior recorded work.** Wiki generation previously grounded on the file tree alone. Grounding now inlines the largest graph communities as candidate sections, high-degree "god nodes" as candidate high-importance pages, a bounded `GRAPH_REPORT.md` excerpt, and — via the new `lib/wiki/knowledge.ts` — the project's recorded decisions and context packs. On this repo that carried 769 communities, 18 decisions, and 9 packs into the authoring prompt.

### Changed

- **MCP tools `list_features` / `get_feature` / `get_feature_file` are now `list_skills` / `get_skill` / `get_skill_file`.** The old names still resolve, via a new `ToolRegistry.registerAlias`, but are kept **out of `tools/list`** — so the advertised tool count stays **20**, agents see the skill names, and any config still calling the old names keeps working. Deliberately **not** renamed: the `features` database table, the `features` key in `INDEX.json`, the tool output field names, and `feature.md` as the on-disk filename — renaming the output field would break the alias's own compatibility contract.
- **Skills resolve through one function.** `skillsRoot(cwd)` resolves `docs/skills` → legacy `docs/features` → greenfield `docs/skills`, never relocating a project's files silently. `featuresRoot` remains as a deprecated delegating alias, so all seven consumers (CLI, MCP server, hooks bridge, sync daemon, web) got the new resolution without changes.
- **Web labels say "Skills"; routes stay under `/features`.** `/skills` and `/projects/<slug>/skills` are added as redirects, so no existing link or bookmark breaks.
- **`coodra start` now points at the next step on success.** It printed bare ports; it now prints the dashboard URL plus `coodra status` / `coodra init`. (The failure path already pointed at `coodra doctor`.)
- **`coodra org switch [orgSlug]` — the argument is now optional.** It was required but only echoed back; org selection happens in the browser picker.
- **Doctor's hook-registration remediation names `coodra agent add|repair claude`** alongside `coodra init`, now that a targeted fix exists.
- **`coodra agents` is documented as the read-only equivalent of `coodra agent status`**, so the two overlapping surfaces no longer read as unrelated.

### Fixed

- **Every project now gets a default policy at birth — the enforcement loop was failing open.** Only 4 of 55 registered projects on the validation machine had a `__default__` policy, so for the rest the bridge allowed an agent `Write` to `.env`: the advertised protection silently did nothing. `ensureDefaultPolicy` now seeds at **both** project-birth chokepoints (`ensureProject` on created, and `get_run_id`'s solo auto-create), and `coodra doctor --fix` backfills existing projects. Live result: 51 policy-less projects → 0, and doctor's enforcement check went red → green.
- **Stale-run reapers cancelled live sessions.** The periodic sweeper judged a run stuck by **age alone**, so any session running longer than 30 minutes was cancelled while still working. `abandonStaleInProgressRuns` was worse: it abandoned other sessions' in-progress runs for a project with **no age or activity check at all**, so opening a second terminal instantly abandoned the first terminal's live run. Both now require that a run has produced no `run_events` since the cutoff — an active session keeps emitting events, an orphaned one does not. **A running hooks-bridge daemon keeps the old behaviour until it is restarted.**
- **The TUI's command catalog offered commands the terminal then refused to run.** Six top-level groups (`metrics`, `agent`, `files`, `graphify`, `jira`, `wiki`) were missing from the category map; a silent fallback meant they still appeared in the Commands view while `isKnownCommand` rejected them. Their IO was also never wired into the in-process runner, so their default `process.exit()` would have terminated the whole TUI once they became reachable. All three are fixed and catalog completeness is now asserted against the real command surface.
- **`coodra graphify build` produced no interactive graph on any real repository.** Graphify skips its HTML visualisation above 5000 nodes and `update` swallows the notice, so `graph.html` never existed for a codebase of consequence (found while building this repo's own 13,982-node graph). `build` now falls back to `graphify export html --node-limit N`, which renders the aggregated community view; `--no-viz` opts out for CI.
- **Graphify's incremental-state file no longer looks like an unexplained stray.** Graphify 0.8.27 writes `graphify-out/manifest.json` even when `GRAPHIFY_OUT` points elsewhere (reproduced against the real binary), so a managed-layout build left a large untracked file at the repository root. It is now recorded in the manifest as a `state-cache` entry — safe to clean under the managed layout, `ask` under the committed legacy layout — rather than deleted, since deleting it forces a full re-extraction on the next build.
- **Deep Wiki grounding silently under-reported the codebase graph.** It looked for a hardcoded `graphify-out/` path (missing the managed layout entirely) and read `json.edges` where the graph format uses `json.links`, so the edge count was always null.
- **`coodra status` reported a blocker that did not exist.** It previewed the first bytes of `context_memory/blockers.md`, so the file's own explanatory header rendered as a pending-blocker warning on a project whose blockers were all resolved. It now counts real entry headings, ignores the format example inside the fenced block, and skips resolved ones.
- **`coodra run list` was unreadable.** 108-character run keys overflowed their column and ran straight into the status word (`…48ccin_progress`). Overflowing cells now keep their separator.
- **A new skill's scaffold pointed at a tool that does not exist.** Every `coodra skill add` wrote `coodra__get_feature(...)` into the generated `feature.md`; it is now `coodra__get_skill`. `coodra skill index` was also the one subcommand still reporting "feature(s)".
- **`coodra uninstall` now stops the daemons before removing files** — all four units, including the port-3001 web service that previously survived an uninstall — and gained `--remove-data` (SQLite only; keeps config and packs).
- **`coodra db restore`'s preflight sees every service.** It checked PID files only, so a launchd- or systemd-managed `mcp-server` and the `web` service sailed past the guard; it now checks all services through both the PID files and the daemon manager.
- **The web dashboard's version is real.** It hardcoded `v 0.4.1`; it now reads `COODRA_CLI_VERSION`.
- **The `/roi` dashboard has a first-run state.** A user with no recorded runs saw a `$0.00` net-value dashboard and a column of `—`; it now explains that metrics appear after the first agent session.
- **Web listings say when projects are hidden.** Org-scoped filtering (deliberate, and unchanged) meant a project belonging to a different org or mode simply vanished from `/projects` and `/graphify` while the CLI reported it as registered. The listings now state how many projects are hidden and why.
- **`list_skills`' tool description was 857 characters against the documented 800-character cap** — trimmed, and the cap is enforced by the manifest end-to-end test.

### Removed

- **22 dead-code items** across the sync daemon, hooks bridge, MCP server, database package, CLI, and web app — zero-reference exports, two dead test seams, a retired error class, and two unused web query modules. One unused dependency (`@hono/zod-validator`) dropped. Internal `featuresRoot` callers migrated to `skillsRoot`, and the bridge's hand-rolled Clerk-token path resolution now reuses the shared helper.
- **Four `--force` flags that did nothing** (`run cancel`, `pack regenerate`, `db restore`, `logout`). A flag a script can pass that has no effect is worse than no flag.

### Documentation

- **41 drifts corrected**, nearly all traceable to one cause: the Skills rename and the tool-count bump reached the code but not the agent-facing prose. The trigger contract claimed 26 tools and instructed agents to call `list_features` / `get_feature` — names absent from `tools/list` — while also stating that unlisted tools do not exist. Corrected there and in `system-architecture.md` §24.4, `README.md` (15 → 20 tools), `docs/DEVELOPMENT.md` (9 → 20), the repository-structure map (no `services/`, no `apps/web`, no `apps/vscode`; the CLI is no longer "future"), the module order (Module 06 is Run Diff), and the marketing tool roster (the retired `query_codebase_graph` removed, the five newer tools added).
- **`.env.example` matches reality.** Removed variables nothing consumes (`NL_ASSEMBLY_PORT`, `SEMANTIC_DIFF_PORT`, the removed `COODRA_DB_OVERRIDE_MODE` knob, unconsumed LLM keys, `COODRA_GRAPHIFY_ROOT`) and documented two that are consumed but were undocumented (`CLERK_JWT_ISSUER`, `COODRA_INVITE_HMAC_SECRET`).

## [0.2.0-beta.27] — 2026-07-12

Field-report remediation (MatrixOcr runs, Windsurf/Devin + Codex agents). Four defects fixed, each verified live against the built bundle; +60 unit tests.

### Added

- **`wiki_save_structure` replace guard.** Re-planning a wiki that already has ≥1 **authored** page now soft-fails with `wiki_exists` (returning the existing `wikiId` + authored/total counts) unless `replace: true` is passed. Previously the re-plan was an unconditional DELETE-then-INSERT, so two agents defaulting to the same project slug silently wiped each other's authored wikis — the root cause of "deep wiki generation seems inconsistent" in the 2026-07-12 field report. A pending-only skeleton still replaces freely, so same-session plan iteration is unaffected. The authoring recipe, trigger contract, and tool manifest document the new contract.
- **`coodra jira enable` detects a pre-existing Atlassian MCP server and asks before adding a second one.** Detection is by URL host (`mcp.atlassian.com`) across **every** `mcpServers`/`mcp_servers` entry — any key (`atlassian-mcp-server`, …), any shape (`url` / `serverUrl` / `npx mcp-remote` shim), including `disabled: true` variants. Interactive runs prompt (`[y/N]`); non-interactive/JSON runs skip with a notice; `--force` proceeds. `coodra init`'s Jira step skips-with-warning the same way, and `coodra jira status` now reports a foreign-keyed Atlassian server as "wired (not Coodra-managed)" instead of the misleading "no atlassian entry". (2026-07-12 field report: enable next to the user's existing `atlassian-mcp-server` produced two Atlassian servers.)

### Fixed

- **Windsurf sessions are no longer misattributed to Codex.** (2026-07-12 field report: a Windsurf/Devin session with `COODRA_AGENT_TYPE=windsurf` correctly stamped was recorded as `codex`.) Three-layer fix: (1) `get_run_id` now trusts the transport-resolved agent identity when it is known — the `agentType` input param only applies when the transport resolves `unknown`. The param is instruction-file text that any agent may parrot: AGENTS.md is a de-facto cross-agent standard, so Windsurf reading a Codex-generated AGENTS.md dutifully passed `agentType: "codex"` and it used to win. (2) On stdio, the per-config `COODRA_AGENT_TYPE` env stamp now takes precedence over the clientInfo-name heuristic (the stamp identifies the exact config entry that launched the server; HTTP keeps clientInfo-first). (3) The client-name mapping learned Windsurf's family names (`codeium`, `cascade`, `devin`) and the substring heuristics check `codex` **last** so it can't shadow other products. Instruction files now say "if you are a DIFFERENT agent reading this file, pass YOUR own type" instead of an unconditional `ALWAYS pass`.
- **`coodra uninstall` cleans the same project root `coodra init` wrote.** Uninstall used raw `process.cwd()`, while init resolves the project root by walking up to the nearest marker (`.git` / `package.json` / …) — so uninstall run from a subdirectory inspected a *different* `.cursor/mcp.json` (and `.mcp.json`, `.codex/config.toml`, `CLAUDE.md`, …) and reported "no coodra entry to remove" while the real entries persisted (2026-07-12 field report). Uninstall now resolves the root identically, prints it (`project root: …`), and includes it in `--json` output as `projectRoot`.
- **Deep-wiki coverage guidance no longer contradicts itself, and grounding no longer silently under-samples.** The authoring recipe's page-count guidance is mode-aware and repo-derived (comprehensive: one page per major module plus cross-cutting pages, typically 12–30, "when in doubt, ADD the page"; concise: 6–12), replacing the old "~8–20 pages" + "prefer fewer, deeper pages" contradiction that produced arbitrary low counts ("why only 11 pages?"). The grounding walk is now breadth-first (a truncated sample represents every top-level area instead of exhausting the cap inside the first alphabetical subtree), the file cap rose 600 → 1500, and a truncated list carries an explicit instruction to enumerate under-represented directories before planning.

## [0.2.0-beta.26] — 2026-07-09

### Added

- **`'ask'` policy tier — now enforced end-to-end.** A policy rule with `decision='ask'` (e.g. the seeded "ask before Bash" rule) propagates through the evaluator → `check_policy` → the hooks-bridge → Claude Code's `permissionDecision: 'ask'` (a real user-confirmation prompt). ## [0.2.0-beta.8] — 2026-05-18

### Fixed

- **`packages/cli/src/commands/start.ts`** — `coodra start --tunnel` now re-installs the web service after the Cloudflare quick-tunnel URL is captured. Pre-fix flow: bootstrap all services (web's plist is generated with no `COODRA_PUBLIC_URL`) → start cloudflared → write `COODRA_PUBLIC_URL=<tunnel-url>` to `~/.coodra/.env`. The running web process never picked up the new env, so `resolveDeploymentBaseUrl()` inside the web process fell through to the `COODRA_HOME` local fallback (returning `http://localhost:3001`). Every URL the web rendered (invite tokens minted via `mintInviteAction`, JWT `iss` claims, `/install/<token>/cli.sh` body, `/api/install/<token>` issuer validation) used localhost instead of the tunnel URL. Result: cross-machine invite redemption failed with iss-mismatch even though the admin's tunnel was perfectly reachable. The fix is to capture the tunnel URL from `orchestrateTunnel` (signature now `Promise<string | null>`), then run `manager.stop('web') → manager.install(updatedUnit) → manager.start('web')` so the plist is regenerated with the fresh env. Cloudflared's target (loopback `:3001`) tolerates the ~2s outage transparently.

### Migration note for admins on beta.7

Users of beta.7 on `--tunnel` had to manually patch `~/Library/LaunchAgents/com.coodra.web.plist` to inject `COODRA_PUBLIC_URL`, then `launchctl bootout && bootstrap` web. On beta.8 the same `coodra start --tunnel` invocation produces a correct plist on first run; no manual patching needed.

## [0.2.0-beta.7] — 2026-05-18

### Fixed

- **`turbo.json`** — root cause of the beta.6 stale-bundle regression. The `build` task's `inputs` glob was hard-coded to `src/**/*.{ts,tsx}`. `apps/web-v2` (Next.js App Router) doesn't have a `src/` directory — its source lives in `app/`, `lib/`, `components/`, `middleware.ts`, and `next.config.ts`. None of those matched the glob, so Turbo's cache hash never changed for web-v2 source edits and it silently replayed an old build (in beta.6's case, a May-16 build from before the `public-url.ts` fix was even written). The bundle script then copied that stale `.next/standalone` into the CLI tarball. CI was green because unit tests run against source, not the bundle. Fixed by switching all task `inputs` to `$TURBO_DEFAULT$` (every tracked file in the package, the Turbo idiom for monorepos with mixed layouts) and adding `.next/**` to the `build` task's `outputs` so Turbo correctly tracks Next.js's standalone output too. The `apps/web-v2/lib/public-url.ts` fix that was authored in beta.6 is now actually present in the bundle.
- **`packages/cli/scripts/prepublish-assert.mjs`** — added a freshness check that walks `apps/web-v2/{lib,app,components,middleware.ts,next.config.ts}` for the newest source mtime and compares against `dist/runtime/web/apps/web-v2/server.js`. If source is newer than the bundle, the publish is refused with a clean-rebuild instruction. The Turbo fix above is the durable fix; this assert is the last-line defense against local-state divergence (e.g., a hand-rolled build that bypassed Turbo).

### Known issue (acknowledged)

- `@coodra/cli@0.2.0-beta.6` on the npm registry has the stale web bundle. Anyone installing `@coodra/cli@beta` between 2026-05-18 ~16:00 and the beta.7 publish will get the broken invite URL. **Mitigation for affected installs:** add `COODRA_PUBLIC_URL=http://localhost:3001` to `~/.coodra/.env`, then `coodra stop && coodra start`. That resolves via the existing `COODRA_PUBLIC_URL` env path (case 1), which has worked since beta.3. beta.7 ships the local fallback (case 3) bundled correctly so the env var is no longer required.

## [0.2.0-beta.5] — 2026-05-18

### Fixed

- **`packages/cli/src/lib/services.ts`**: web service plist now emits `HOSTNAME=::` (IPv6 wildcard, dual-stack) instead of `HOSTNAME=127.0.0.1`. beta.4's narrower `127.0.0.1` bind made the CLI's IPv4 healthcheck land, but broke team-mode `force-dynamic` routes: Next.js 15.5 standalone has an internal render-proxy (`next/dist/server/lib/router-utils/proxy-request.js`) that does a server-side `fetch('http://localhost:${PORT}/<route>')` to itself for force-dynamic routes. macOS resolves `localhost` to `::1` first; with an IPv4-only bind the self-proxy had no listener; requests hung; `/api/healthz` (which has `export const dynamic = 'force-dynamic'`) never returned; `coodra start` again reported "Coodra Web did not become healthy on :3001 within 30000ms" even though Next was running. `::` with the kernel-default `IPV6_V6ONLY=0` accepts both native IPv6 (`::1`) AND IPv4 connections (via IPv4-mapped IPv6), so the Next self-proxy AND the CLI's IPv4 healthcheck both land cleanly. Cold start to first 200 on `/api/healthz` is ~2 seconds on a developer laptop.
- The regression-locking test in `packages/cli/__tests__/unit/services.test.ts` is updated to assert `HOSTNAME=::`. The test docstring records the full beta.3 → beta.4 → beta.5 regression history so a future refactor can't silently re-introduce either prior failure.

### Known trade-off

- **Web is now LAN-reachable** (not loopback-only) because `::` listens on all IPv6 interfaces (and IPv4-mapped IPv6 is accepted by default on macOS/Linux). In team mode every route is gated behind Clerk auth, so a LAN attacker still needs a valid session — but solo-mode users on hostile networks should add a local firewall rule. A loopback-only dual-stack bind (separate `listen()` calls on `127.0.0.1` and `::1`) is tracked as a follow-up but requires wrapping Next.js's auto-generated `server.js`; not in this release.

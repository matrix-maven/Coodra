# Changelog

All notable changes to `@coodra/cli` are recorded here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Pre-release tags do not guarantee SemVer; breaking changes between beta releases are possible and called out per entry.

## [Unreleased]

### Changed

- **2026-08-03 — `coodra-work` redesign, round 2: `SessionStart` now injects recent Context Packs + decisions instead of Work Pack metadata, and decisions/Context Packs can link to more than one Work Pack.** Follow-up to the initial `coodra-work` redesign above. Two fixes:
  - **SessionStart content swap.** The previous pass had `SessionStart` surface an "Active Work Packs" block (slug/status metadata) via `work_pack_status`. That's navigational, not substantive, and belongs to `coodra-work`'s own explicit resume flow (its step 2 already calls `work_pack_status`). `SessionStart` (`apps/mcp-server/src/tools/lifecycle-event/handler.ts`) now instead calls `list_context_packs` (most-recent 3, with excerpts) and `query_decisions` (most-recent 5, project-wide) and injects a `## Recent context` block — substance the agent can reason against, not just a pointer.
  - **Direct many-to-many decision/Context-Pack ↔ Work Pack linking.** Previously a decision's Work Pack membership was derivable only transitively (`decisions.run_id → runs.id → runs.work_pack_id`), which meant (a) a related-but-different pack could never see another pack's decisions via `query_decisions{workPackId}`, and (b) `runs.work_pack_id` being a single mutable column meant a run touching two packs in sequence could silently reassign earlier decisions when queried transitively. New join tables `work_pack_decision_links` and `work_pack_context_pack_links` (both dialects, migration `0025_work_pack_content_links` postgres / `0023_work_pack_content_links` sqlite — schema-only, no data migration) fix both: `record_decision` gained optional `workPackSlugs`, `save_context_pack` gained optional `alsoLinkWorkPackSlugs`, both additive to their existing single-pack linking. `query_decisions`'s `workPackId` filter now matches either the transitive `runs.work_pack_id` link or the new direct tag, and gained `includeRelated` to also pull decisions from packs linked via `work_pack_relationships` one hop out — e.g. a decision made on Pack 1 that a related, concurrently-worked Pack 2 should already know about. Also fixed in passing: `query_decisions`'s `workPackId`/`issueRef` filters were previously only reachable via one narrow path per decision; `selectDecisions` now composes the transitive and direct-link conditions with `OR` rather than requiring the caller to already know which mechanism applies.
- **2026-08-03 — `work_pack_upsert`'s `status` field now has the same canonical/native split as `packType`/`source.issueType`.** Previously undocumented (`status: z.string()` with no `.describe()`); now documents a small recommended set (`draft`, `in_progress`, `in_review`, `blocked`, `done`) for the top-level `status`, with `source.status` clarified as where the provider's own raw status label (e.g. Jira "In Review") belongs instead. Soft governance only — still a free string, not a hard `enum`, so a future provider's own status vocabulary doesn't require a Coodra code change. The `coodra-work` skill's Model section (identical across all three plugins) mentions the split alongside its existing `packType` explanation.
- **2026-08-03 — `coodra-jira-work` renamed and generalized to `coodra-work`; Work Packs are no longer Jira-only.** The bundled skill (identical content across `claude-plugin.ts`/`codex-plugin.ts`/`cursor-plugin.ts`) now covers a Jira issue, a GitHub/GitLab PR, or a manually-created pack under one procedure instead of a Jira-only recipe — `work_pack_upsert`'s `packType` (`apps/mcp-server/src/tools/work-pack-upsert/schema.ts`) gained `pr` alongside the existing epic/feature/story/task/bug/subtask/unknown set as Coodra's canonical cross-provider classification, with `source.issueType` clarified as where the provider's own raw type label lives (e.g. Jira "Story", GitHub "pull_request") and `source.provider` no longer described as Jira/Atlassian-specific. `coodra work import`'s Jira-shaped regex (`/^[A-Z][A-Z0-9]+-\d+$/`) and `link_run_to_issue`'s matching regex (`/^[A-Za-z][A-Za-z0-9]{1,9}-\d+$/`) were both removed — a bad key now surfaces as "not found" from the provider's own MCP (Rovo, GitHub, GitLab) instead of a Coodra-side format rejection; there was never a plan to add a persistent Atlassian project-key config, so none was built. `query_decisions` gained an optional `workPackId` filter spanning every run tied to a Work Pack (not just the current session's `runId`/`issueRef`), for packs resumed across multiple sessions; fixed the `issueRef` filter silently no-opping on the Postgres/team-mode branch of the handler while touching the same function. The `UserPromptSubmit`-time `parseJiraWorkIntent` phrase-detection hook (`packages/shared/src/work-intent.ts`, deleted) — which scanned every prompt for a Jira-key-shaped string and only ever worked for Claude/Codex, since Cursor's `beforeSubmitPrompt` has no context-injection field — is replaced by a state-based check on `SessionStart` (see the follow-up entry below for what it actually injects — this initial pass injected Work Pack metadata, since revised). Sync-back (posting a session summary to the external tracker/PR) is redesigned to reuse decisions already recorded during implementation instead of a bespoke rendering tool: the skill now calls `query_decisions` and composes its own comment from the returned decisions, rather than `prepare_jira_comment` — that tool is superseded and no longer recommended by the skill, though it remains registered (unused elsewhere) as a soft-deprecation rather than a breaking removal.

### Added

- **2026-08-04 — New `coodra wiki ask "<question>"` command: a connected-Markdown Deep Wiki mirror, retrieval-only (Coodra runs no LLM), local-first with a DB fallback.** Researched Google Cloud's Open Knowledge Format (OKF v0.1) as inspiration per user request — a directory of cross-linked Markdown files with light YAML frontmatter, walkable without a database or index. The Deep Wiki's on-disk mirror already wrote plain Markdown per page, but thinly (frontmatter had only `pageId`/`wikiId`/`title`/`state`/`updatedAt`, no rendered cross-links, no description) and a `.coodra/wiki/okf/` scaffold directory existed with nothing ever written into it — a dead "future OKF export" stub, since retired along with `WIKI_OKF_DIR_RELPATH`/`wikiPagePath`. The mirror now lives at `.coodra/wiki/<slug>/md/` (`wikiMdDir`/`wikiPageMdPath`/`wikiMdIndexPath` in `packages/shared/src/wiki/paths.ts`): each page (`<pageId>.md`) gets enriched frontmatter (`type`, `description`, `importance`, `parentId`, `relatedPageIds`) and a rendered "## Related pages" section with literal `[Title](./<id>.md)` links, so the corpus is walkable on disk with no DB round-trip — plus a generated `index.md` table of contents, written once right after `wiki_save_structure` succeeds since everything it needs is already in the just-saved structure. `renderWikiRecipe()` (`packages/cli/src/lib/wiki/recipe.ts`) instructs the coding agent to write this shape; the bundled `coodra-wiki` skill (identical across `claude-plugin.ts`/`codex-plugin.ts`/`cursor-plugin.ts`) gained a new step telling the agent to run `coodra wiki ask` before re-scanning the repo for how-does-X-work questions. `coodra wiki ask` itself (`runWikiAskCommand` in `packages/cli/src/commands/wiki.ts`) reads `.coodra/wiki/<slug>/md/` first — a hand-rolled, dependency-free scorer (`scoreWikiCorpus` in new `packages/shared/src/wiki/md-mirror.ts`; title/description/body weighted, OR semantics with a coverage bonus rather than strict AND, since natural-language questions against a small per-repo corpus would too often return zero hits under AND) — and never opens the DB on that path. It falls back to the DB (parsing per-page title/description out of `wikis.structureJson`, since that's the only place they live — no queryable column — joined in-memory with `wikiPages.contentMarkdown`) when the local mirror is missing, empty, or `--refresh` is passed; the same condition transparently covers pre-existing flat-layout mirrors too, no special-case migration needed. Output is always a ranked list of candidate pages + excerpts, never a synthesized answer — the calling agent reads the winning files and composes the answer itself, matching how `search_packs_nl` already works. Deliberately deferred: a SQLite FTS5/Postgres tsvector migration for `wikis`/`wiki_pages` (the local-file path is primary and already has richer flattened per-page metadata than a raw DB row without JS-side JSON parsing; the DB path is a rare degraded-mode fallback over a small per-project table where an in-memory scorer is adequate) and a new MCP `wiki_ask` tool for team-mode/cloud-synced access when a checkout hasn't run `coodra wiki build` locally (a distinct feature deserving its own design pass).
- **2026-08-03 — `search_packs_nl`, `query_decisions`, and `work_pack_status` now use real BM25-ranked full-text search instead of LIKE-substring matching.** Follow-up to the `coodra-work` redesign above — with `SessionStart` now auto-injecting recent Context Packs/decisions, `coodra-context`'s remaining value is targeted retrieval of *older* material a long-running session needs to be reminded of ("remember we did this earlier"), which needs relevance ranking, not substring luck. New hand-authored migrations (outside the Drizzle TS schema, same convention as the existing dead `context_packs_vec`/`pgvector-hnsw` infra they sit next to) add SQLite FTS5 virtual tables + sync triggers (`context_packs_fts`, `decisions_fts`, `work_packs_fts` — `packages/db/drizzle/sqlite/0024_fts_search.sql`) and Postgres generated `tsvector` columns + GIN indexes (`packages/db/drizzle/postgres/0026_fts_search.sql`), ranked via `bm25()`/`ts_rank()` respectively (sign-normalized in application code so a result's `score` always means "higher is more relevant" regardless of dialect). `search_packs_nl`'s previously-always-`null` `score` field is now populated for real, ranking title + content_excerpt. `query_decisions{query}` now ranks description + rationale and composes with its existing `runId`/`issueRef`/`workPackId`/`includeRelated` filters via the established id-resolution-then-`inArray` pattern. `work_pack_status` gained a new optional `query` param (it had no search at all before) ranking title + spec/implementation/sync markdown, requested explicitly since Work Packs benefit from the same retrieval need. All three require every word in a multi-word query to appear (implicit AND) rather than substring matching. Vector/semantic search remains a deliberately separate later phase — the existing `summaryEmbedding`/`context_packs_vec` infrastructure stays unused. Postgres side is not live-verified in this environment (no local Postgres/Docker available); recommended pre-merge check is `pnpm -w docker:up` + `DATABASE_URL=... pnpm --filter @coodra/db test:integration`.
- **2026-08-03 — New `link_run_to_pr` MCP tool binds a run to a PR/MR reference.** Sibling to `link_run_to_issue`, writing the previously-unused `runs.pr_ref` column instead of `runs.issue_ref` — a run can now be bound to a tracker issue and a PR/MR at the same time (two independent columns), the common flow of pulling a Jira issue then opening a PR against it. No format validation, matching `link_run_to_issue`'s relaxed validation above. Tool count 22 → 23.

- **2026-08-02 — COOD-11 follow-up — Codex plugin install/remove now goes entirely through the `codex plugin` CLI, against Coodra's own dedicated marketplace instead of the user's shared "personal" one.** Reported live: Coodra was hand-writing `~/.agents/plugins/marketplace.json` (Codex's "personal" marketplace — the user's own namespace, which can hold their other plugins) and hand-deleting `~/.codex/plugins/cache/personal/coodra/` on removal, so a Coodra edit could clobber unrelated entries in a file it didn't own, and removal had to guess at a cache-directory shape Codex itself owns. Verified live against `codex-cli 0.146.0-alpha.9.2`: `codex plugin marketplace add <path>` requires the path to contain a nested `.agents/plugins/marketplace.json` (a bare `marketplace.json` at the root is rejected), and `codex plugin add <plugin>@<marketplace>` installs and enables in one idempotent call with no separate cache management needed. Coodra's marketplace source now lives at `~/.coodra/codex-marketplaces/coodra/` (named `"coodra"`, not `"personal"`), and `installCodexPlugin`/`removeCodexPlugin` (`packages/cli/src/lib/agents/codex-plugin.ts`) call the Codex CLI directly for the actual marketplace/plugin registration and removal — there is no hand-write or hand-delete fallback for that step. The Codex CLI is resolved via `which codex` first, then known ChatGPT-desktop bundle locations (`/Applications/ChatGPT.app/Contents/Resources/codex`) when it isn't on PATH yet; if found only via a bundle path, the install still proceeds against the resolved absolute path, with a one-time note suggesting the user symlink it onto PATH for their own convenience. If the CLI can't be found at all, Coodra still writes its own marketplace/plugin source files to disk (so a later `coodra agent add codex` re-run, or the user running `codex plugin marketplace add` by hand, has something valid to point at) but reports the plugin as not actually installed. `CodexCliRunner`/`ClaudeCliRunner` overrides are now threaded through the full `AgentAdapter` chain (`AgentPathContext`/`AgentContext`/`AgentRemoveContext` → `resolveAgentWiringContext` → `runAgentAddCommand`/`runAgentStatusCommand`/`runAgentRemoveCommand` → `uninstall.ts`'s `removeGlobalNativePlugins`), closing a pre-existing gap where both agents' install/status/remove always fell back to shelling out to the real `claude`/`codex` binaries with no way for tests to inject a fake runner — this was previously only caught for Claude at the doctor-check layer. Also fixed `codexPluginPaths(userHome)` being called without the resolved `coodraHome` override in `agent.ts`'s post-install machine-manifest recording (`packages/cli/src/commands/agent.ts`), which would have recorded the wrong `pluginPath` for a custom `COODRA_HOME`.
- **2026-08-02 — Claude plugin removal now also deregisters the marketplace via `claude plugin marketplace remove`, instead of relying only on a hand-edit of `known_marketplaces.json`.** Auditing `claude-plugin.ts` against `code.claude.com/docs/en/plugin-marketplaces` and `plugins-reference` confirmed the install path (`claude plugin marketplace add` + `claude plugin install --scope user`) and the plugin-removal call (`claude plugin uninstall --scope user`) both matched the documented CLI exactly, but `removeClaudePlugin`'s `uninstallPlugin()` never called `claude plugin marketplace remove` — the marketplace registration itself was always stripped by hand-editing `known_marketplaces.json`, even when the CLI was available and could have done it. `ClaudeCliRunner.uninstallPlugin` now issues both `claude plugin uninstall coodra@coodra --scope user` and `claude plugin marketplace remove coodra --scope user`, mirroring the two-call shape `CodexCliRunner.uninstallPlugin` already uses for `codex plugin remove` + `codex plugin marketplace remove`. The hand-written `known_marketplaces.json`/cache cleanup is unchanged and still runs unconditionally afterward as an idempotent backstop for when the CLI is unavailable or fails.

### Added

- **2026-08-02 — Cursor is now a third supported native-plugin agent, alongside Claude Code and Codex.** `coodra agent add cursor` installs a global native plugin bundling skills, the Coodra MCP server, managed Graphify, and lifecycle hooks — same shape as Claude/Codex, but architecturally simpler: live research (installed `cursor-agent`, inspected the real `~/.cursor/plugins/` layout including an actually-installed third-party plugin, and read cursor.com's plugin/hooks/mcp/permissions docs) found Cursor's `cursor-agent plugin marketplace` CLI is for git-hosted, account-authenticated distribution only (`plugin marketplace list` fails outright without login) — not applicable to a local install. The real mechanism is a plain directory dropped at `~/.cursor/plugins/local/coodra/`, which Cursor discovers on its own; install/remove are therefore pure filesystem writes/deletes with no CLI runner to inject, unlike `claude-plugin.ts`/`codex-plugin.ts`. Cursor hooks are pure command scripts (stdin/stdout JSON, no Claude-style built-in `mcp_tool` hook type), so a new Cursor-specific `hook-runner.mjs` spawns the Coodra MCP server over stdio and calls `lifecycle_event`, same as Codex's; the mcp-server's `lifecycle_event` handler gained a third `shapeHookOutput` branch producing Cursor's narrower per-event output shapes (`preToolUse` only supports `allow`/`deny`, no `ask` — an upstream `ask` policy decision collapses to `allow`; `beforeSubmitPrompt`, Cursor's `UserPromptSubmit` equivalent, has no context-injection field at all, so Jira-work-intent context that Claude/Codex inject there is lost for Cursor, though `sessionStart`'s session-contract injection is unaffected; `stop` can't force a block the way Claude/Codex's `decision:'block'` can). Cursor has no `ConfigChange`-equivalent hook event, so that hook is simply absent for this agent. Verified end-to-end live: built the plugin against a scratch `HOME`, then invoked the generated `hook-runner.mjs` directly for both `sessionStart` (returned the full session contract + workflow policy + policy-projection-drift context) and `preToolUse` (`{"permission":"allow"}`) — full round-trip through the real MCP server. The exact hook payload field names are taken from Cursor's public docs, not live-verified against a running Cursor session (no logged-in Cursor account was available); a supervised live smoke test is recommended before relying on this for real policy enforcement. Deliberately out of scope for this pass: a native-permissions-projection compiler writing Coodra's DB policy rules into Cursor's own `.cursor/cli.json` `permissions.allow/deny` format (mirroring what Claude/Codex already get) — runtime policy enforcement via the `preToolUse` hook works today; the static projection is a planned follow-up.
- **2026-08-01 — COOD-25 — Added the audit-ready tenant attribution schema foundation.** SQLite and Postgres now carry org/project attribution across audit-relevant tables, retain `decisions.run_id` while adding `decisions.project_id` and `decisions.org_id`, and include `updated_by_user_id` on mutable user-owned records that already expose `updated_at`. A new append-only `audit_events` table records actor, subject, action/result, metadata, and hash-chain fields for the future EE audit trail. Core write paths now stamp attribution where it is reliably available today, covering run creation, run events, context packs, decisions, and policy decision recording; schema parity tests and migration-lock coverage were updated alongside the new migrations.

### Removed

- **2026-08-02 — BREAKING — Dropped Cursor, Windsurf, Devin, Cascade, and Codeium agent support; Coodra now supports only native Claude Code and Codex plugins.** Removed the per-agent MCP/instruction-file adapters (`cursor-merge.ts`, `windsurf-merge.ts`), the shared hooks-bridge payload schemas/adapters and their `/v1/hooks/{windsurf,cursor}` routes, the shell hook-adapter scripts (`scripts/hook-adapters/{windsurf,cursor}-coodra.sh` + `install.sh`), and the `devin`/`cascade`/`codeium` input aliases from the `AgentAdapter` registry. `coodra agent add/status/remove/repair` and `coodra agents` now only accept `claude | codex | all | detected`. `graphify-wire.ts` collapsed to a Codex-only explicit-wiring path now that Claude Code and Codex are both native-plugin-managed (Claude Code was already a no-op here; Codex gets the same treatment). The mcp-server `agent-type` mapping, the shared `HookEvent` schema, and the `get_run_id`/`check_policy` input schemas now accept only `claude_code | codex | unknown` — no alias resolution for the removed clients and no migration path for their historical `runs.agent_type`/`policy_decisions` rows. `packages/cli/package.json` no longer exports `./lib/init/jira-wire` (see below) or any per-IDE merge helper.
- **2026-08-02 — BREAKING — Removed the `coodra jira` command (`enable`/`disable`/`status`).** The CLI no longer wires Atlassian's Rovo remote MCP server into agent configs; that per-IDE wiring depended on the same removed adapter substrate. Connect Rovo directly via your agent's own native MCP/connector settings in the meantime. Coodra's own Jira-adjacent MCP tools — `link_run_to_issue`, `prepare_jira_comment`, and Jira-linked Work Packs (`work_pack_upsert`, the Work Pack detail page's ticket metadata + "Open Jira ↗" link) — are unaffected; they don't depend on how Rovo got wired. A Coodra-managed Jira integration (a project-scoped site/project config so the agent doesn't need to be told which Jira instance/project to use every session) is planned as a redesign, not yet implemented. The web-v2 `/settings/integrations` Jira card and the team-onboarding "wire your tools" Jira step were removed accordingly.
- **2026-08-02 — BREAKING — Removed `coodra graphify enable`/`disable`, the explicit per-IDE Graphify MCP wiring path.** Graphify wiring is now Coodra-owned end to end: `coodra agent add <agent>` installs the native Claude Code / Codex plugin, which already bundles a managed `graphify` MCP entry pointed at the shared machine runtime and `.coodra/graphify/out/graph.json` alongside `coodra` — there is no remaining scenario where a separate wiring step is needed. `coodra graphify status` stays as a read-only probe of that wiring plus the graph artifact state; `build`/`open`/`clean` are unaffected. Also removed `docs/feature-packs/` entirely (retired Feature Pack spec history superseded by Agent Recipes and Work Packs under `.coodra/`) and the now-dead `detectGraphifyLayout` helper that only existed to drive the removed `enable` command's migration prompt.
- **2026-08-02 — COOD-11 follow-up — Retired `deep-wiki-author` as a separately-bundled skill/recipe; `coodra-wiki` is now the only wiki skill.** COOD-11's own acceptance criteria said "there is only one canonical wiki implementation," but the shipped result kept `deep-wiki-author` as a second bundled native-plugin skill *and* a third copy scaffolded as a project-local Agent Recipe under `.coodra/recipes/deep-wiki-author/` on every `coodra wiki build`. Traced the redundancy: `deep-wiki-author`'s bundled body shipped with placeholder params and its own text said "run `coodra wiki build` first... read job.md for the exact params" — i.e. even triggered directly it required the same bootstrap `coodra-wiki` already handles, so its only non-redundant value was a more eagerly-matching skill description. Folded that trigger phrasing (generate/build/refresh/update the deep wiki, document the architecture) into `coodra-wiki`'s own description, removed `deepWikiFeatureFrontmatter`/`renderDeepWikiFeatureBody` and the recipe-scaffolding step from `coodra wiki build`/`generate` (and their now-meaningless `--force` flag, which only ever controlled that scaffold's overwrite), and dropped the `deep-wiki-author` skill from both the Codex and Claude Code native-plugin bundles (including their `skills` health-check probes, now checking for `coodra-wiki` instead). `.coodra/wiki/job.md` — the actual per-run parameterized recipe instance — is unaffected; it was never redundant.
- **2026-08-02 — BREAKING — Removed the pre-rename `list_skills`/`get_skill`/`get_skill_file`/`list_features`/`get_feature`/`get_feature_file` MCP tool aliases.** These were kept as `ToolRegistry.registerAlias` hidden synonyms when Skills/Features were renamed to Agent Recipes on 2026-07-31, so no in-flight agent config would break mid-upgrade. That transition window is over — call `list_recipes`/`get_recipe`/`get_recipe_file` directly. The generic `ToolRegistry.registerAlias` mechanism itself is unaffected (still available for future renames); only these six call sites in `apps/mcp-server/src/tools/index.ts` were removed. Aliases were always excluded from `tools/list` by design, so this does not change the advertised tool count (still 22 — a stale `boot.test.ts`/`boot-team-mode-local-sqlite.test.ts` drift-log assertion of 21 was also fixed in the same pass; it predated this change, missing the Work Pack foundation's `work_pack_upsert`/`work_pack_status` addition on 2026-07-31).
- **2026-08-02 — Removed the `coodra skill`/`coodra feature` Commander aliases for `coodra recipe`.** Left over from the same Skills/Features → Agent Recipes rename as the MCP tool aliases above; kept as a migration courtesy but only added confusion going forward (three names for one command, two of which no longer match anything else in the CLI's vocabulary). `coodra recipe {add,list,show,edit,index}` is now the only name.
- **2026-08-02 — Removed the deprecated `coodra wiki generate` alias for `coodra wiki build`.** Same rationale as the `recipe` aliases above — one name per command.
- **2026-08-02 — Stopped suggesting `/graphify .` "inside your agent" as a richer alternative to `coodra graphify build`.** Coodra installs and manages only Graphify's Python package (the structural CLI + the managed MCP server bundled into every native plugin) — it never installs or wires any native agent-plugin/slash-command surface Graphify itself might separately ship. Suggesting `/graphify .` in CLI help text, error messages, and hints assumed the user had also, independently, installed Graphify's own plugin into that specific agent — something Coodra can't verify and usually isn't true, so the suggestion pointed users at a command that just doesn't exist for them. `coodra graphify build`/`open`/`clean` and the `coodra graphify` command description no longer mention it. (Unrelated, unchanged: the *lowercase, unslashed* `graphify .` mentioned in a couple of code comments refers to the wrapped CLI's own default subcommand when Coodra invokes it headlessly — that's accurate documentation of the wrapped tool's behavior, not a user-facing suggestion, and stays.)

### Fixed

- **2026-08-02 — `coodra-jira-work`'s bundled skill no longer promises a Work Pack auto-save that doesn't happen.** The skill's own text claimed "the Coodra SessionEnd hook updates the linked Work Pack with the implementation overview and changed files" — a description of `apps/hooks-bridge`'s retired `saveAutoContextPack` behavior. The native `lifecycle_event` handler all three plugins actually use (`apps/mcp-server/src/tools/lifecycle-event/handler.ts`) has always had a no-op `SessionEnd` case, so this never happened for any agent under the native-plugin architecture. The skill (identical content in `claude-plugin.ts`/`codex-plugin.ts`/`cursor-plugin.ts`) now tells the agent to call `coodra__save_context_pack` itself before ending the session instead of asserting a hook will do it. Also fixed `coodra wiki`'s command description, which still said "Claude Code / Codex" and omitted Cursor.
- **2026-08-02 — `coodra agents`/`coodra agent status` no longer tell you to run a nonexistent `coodra init --ide <agent>` flag, or claim `coodra init` wires native agent plugins.** `coodra init` only ever writes project-local `.coodra/{config.json,manifest.json,...}` — it has never called into the `AgentAdapter` registry (`packages/cli/src/lib/agents/`) that actually installs native plugins; only `coodra agent add <agent>` does that. The per-agent `howToEnable` hints in `coodra agents`' JSON/table output, its trailing hint line, and the `mcpJsonState` "no coodra entry" note all previously pointed at `coodra init` (and, for Claude/Codex, a `--ide` flag that has never existed on any registered `program.ts` command — `detect.ts`'s `resolveIdeSelection`/`IDE_ORDER` machinery is real but only consumed today by `coodra install`'s detection summary, never by an actual `--ide` CLI option). All four now correctly point at `coodra agent add <agent>`. `agent.ts`'s own module doc comment had the same inversion (crediting `coodra init` with "wiring every detected agent in one onboarding pass," a capability that actually belongs to `coodra agent add all`) and is corrected too.
- **2026-08-02 — `coodra uninstall` now tells you to restart your agent, since a live agent session ignores it entirely until you do.** `uninstall`/`uninstall --purge` deletes on-disk state (the DB, plugin config, marketplace registration) but has no way to reach into an already-running Claude Code / Codex session and stop its already-spawned `coodra` MCP server subprocess — that process keeps running against whatever it had open at boot regardless of what gets deleted afterward. Observed effect: `coodra uninstall --purge` removes `~/.coodra/data.db`, but a live session's still-running MCP server (better-sqlite3 opens without `fileMustExist`, and mcp-server auto-migrates once at boot) transparently recreates an empty DB file on the next tool call and keeps answering — Work Packs, decisions, everything — against that fresh, empty store, with no error to signal anything changed. `coodra uninstall`'s output now ends with a hint to restart the agent so the old subprocess actually gets torn down.

## [0.2.0-beta.28] — 2026-07-24

Six phases of the stakeholder enhancement roadmap plus a whole-product QA sweep. Two user-facing renames (`coodra skill`, the three `*_skill*` MCP tools) ship with aliases so nothing existing breaks. Every phase was validated live on a real machine before the next one started.

### Added

- **`coodra agent add|status|remove|repair <agent>` — per-agent wiring as a first-class command group.** Wiring one coding agent used to mean re-running the whole `coodra init` and accepting whatever it detected; there was no way to add an agent later, repair a drifted config, or strip one agent without stripping all. The new web section lists every project's graph status, renders the report, and embeds the interactive graph.

Grounding now inlines the largest graph communities as candidate sections, high-degree "god nodes" as candidate high-importance pages, a bounded `GRAPH_REPORT.md` excerpt, and — via the new `lib/wiki/knowledge.ts` — the project's recorded decisions and context packs. ### Fixed

- **Every project now gets a default policy at birth — the enforcement loop was failing open.** Only 4 of 55 registered projects on the validation machine had a `__default__` policy, so for the rest the bridge allowed an agent `Write` to `.env`: the advertised protection silently did nothing. `ensureDefaultPolicy` now seeds at **both** project-birth chokepoints (`ensureProject` on created, and `get_run_id`'s solo auto-create), and `coodra doctor --fix` backfills existing projects. Live result: 51 policy-less projects → 0, and doctor's enforcement check went red → green.
- **Stale-run reapers cancelled live sessions.** The periodic sweeper judged a run stuck by **age alone**, so any session running longer than 30 minutes was cancelled while still working. `abandonStaleInProgressRuns` was worse: it abandoned other sessions' in-progress runs for a project with **no age or activity check at all**, so opening a second terminal instantly abandoned the first terminal's live run. Both now require that a run has produced no `run_events` since the cutoff — an active session keeps emitting events, an orphaned one does not. **A running hooks-bridge daemon keeps the old behaviour until it is restarted.**
- **The TUI's command catalog offered commands the terminal then refused to run.** Six top-level groups (`metrics`, `agent`, `files`, `graphify`, `jira`, `wiki`) were missing from the category map; a silent fallback meant they still appeared in the Commands view while `isKnownCommand` rejected them. Their IO was also never wired into the in-process runner, so their default `process.exit()` would have terminated the whole TUI once they became reachable. All three are fixed and catalog completeness is now asserted against the real command surface.
- **`coodra graphify build` produced no interactive graph on any real repository.** Graphify skips its HTML visualisation above 5000 nodes and `update` swallows the notice, so `graph.html` never existed for a codebase of consequence (found while building this repo's own 13,982-node graph). `build` now falls back to `graphify export html --node-limit N`, which renders the aggregated community view; `--no-viz` opts out for CI.
- **Graphify's incremental-state file no longer looks like an unexplained stray.** Graphify 0.8.27 writes `graphify-out/manifest.json` even when `GRAPHIFY_OUT` points elsewhere (reproduced against the real binary), so a managed-layout build left a large untracked file at the repository root. ## [0.2.0-beta.5] — 2026-05-18

### Fixed

- **`packages/cli/src/lib/services.ts`**: web service plist now emits `HOSTNAME=::` (IPv6 wildcard, dual-stack) instead of `HOSTNAME=127.0.0.1`. beta.4's narrower `127.0.0.1` bind made the CLI's IPv4 healthcheck land, but broke team-mode `force-dynamic` routes: Next.js 15.5 standalone has an internal render-proxy (`next/dist/server/lib/router-utils/proxy-request.js`) that does a server-side `fetch('http://localhost:${PORT}/<route>')` to itself for force-dynamic routes. macOS resolves `localhost` to `::1` first; with an IPv4-only bind the self-proxy had no listener; requests hung; `/api/healthz` (which has `export const dynamic = 'force-dynamic'`) never returned; `coodra start` again reported "Coodra Web did not become healthy on :3001 within 30000ms" even though Next was running. `::` with the kernel-default `IPV6_V6ONLY=0` accepts both native IPv6 (`::1`) AND IPv4 connections (via IPv4-mapped IPv6), so the Next self-proxy AND the CLI's IPv4 healthcheck both land cleanly.

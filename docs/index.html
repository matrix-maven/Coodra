Supercharge your coding agent.

Coodra is a local-first plugin architecture for AI coding agents: native agent plugins install Coodra MCP, the lifecycle_event hook tool, managed Graphify, recipes, Deep Wiki, durable memory, and policy governance so sessions start with context and end with evidence.

/01 — Foundation

What Coodra is, in one breath.

Read first
~3 min

A coordination layer between human architects and AI coding agents — Claude Code, Codex, Cursor, Devin, Antigravity, and MCP-speaking clients. It runs locally, installs through native plugins, and routes lifecycle events through Coodra's MCP (Model Context Protocol) server.

/ plugin

Native agent plugins

Generated plugin bundles install the Coodra MCP server, the lifecycle_event hook tool, managed Graphify MCP entry, and task skills for context, recipes, wiki, Work Packs, and graph-aware development.

Claude · Codex · Cursor · Devin · Antigravity
/ memory

Context Packs

Context Packs, decisions, Work Packs, wiki pages, recipes, and run history live in SQLite/Postgres. Agents see a manifest at boot, then pull the specific memory they need through MCP tools.

Measurable pull-through, not prompt stuffing
/ guardrail

Policy enforcement

Pre-tool-use checks, kill switches, native advisory rules, and audit rows keep humans in charge. Coodra returns a verdict only when it has a rule; otherwise the agent's native permission system remains authority.

Fail-open engine · append-only audit

/01.1Design principles

Five things that are true everywhere in the codebase, and that any contribution must respect.

Local-first
Everything useful runs on your laptop first. SQLite is the hot-path store in solo mode and remains the local write path in team mode; sync is asynchronous.
Fail-open
If the policy engine throws, times out, or the breaker opens — the verdict is ALLOW. Coodra never blocks the agent because of its own faults. packages/policy/src/policy.ts — FAIL_OPEN_RESULT
Append-only audit
Policy decisions and decisions records are never updated or deleted. Idempotency keys gate writes. Resumed kill-switches keep the row, just stamp resumed_at. ADR-007
Production-grade
Plugin files, MCP registrations, wiki pages, Graphify artifacts, and package contents are treated as real product surfaces. If a user can depend on it, tests and docs should name it.
Bind to 127.0.0.1
Every long-running process listens on loopback by default. Hooks, MCP HTTP transport, web UI. Nothing exits the laptop unless the operator sets DATABASE_URL.
/02 — Onboarding

Five minutes to your first run.

Solo mode
Zero network

If you have Node 22, pnpm, and a supported agent installed locally, you are a few commands away. Solo mode is the default after coodra init; native plugins carry the MCP and lifecycle wiring.

/00

Confirm the prereqs.

You need Node 22.16.0 (pinned in .nvmrc), pnpm 10.33.0 via corepack, git, and a supported agent installed locally. macOS uses launchd; Linux uses a fallback daemon manager with PID files.

terminal · prereq check
# Versions Coodra pins to
nvm use            # 22.16.0 per .nvmrc
corepack enable    # activates pnpm 10.33.0
node --version    # → v22.16.0
pnpm --version    # → 10.33.0
/01

Install the CLI.

The only published artefact is @coodra/cli. It ships as a self-contained bundle — bring-your-own SQLite native module is rebuilt on install.

terminal · install
npm i -g @coodra/cli
# or, in a workspace:
pnpm add -D @coodra/cli
/02

Initialise the project.

From your repo root, run coodra init. It registers the project under .coodra/, seeds the default policy, creates recipe/wiki/graphify/Work Pack directories, and leaves repo-root MCP config user-owned.

repo root
coodra init
# picks the slug from git remote, asks which IDE,
# defaults to --solo. Use --team to wire Clerk.

# What it creates:

.coodra/manifest.json project registration ledger
.coodra/recipes/      agent recipe workspace
.coodra/graphify/     managed structural graph output
.coodra/wiki/         Deep Wiki grounding + mirrors
~/.coodra/data.db     SQLite primary store
~/.coodra/.env        solo-mode env, ready to grow into team
/03

Start the daemons.

One command brings up the local MCP server and web UI. Native plugins report SessionStart, prompt, tool, compaction, and SessionEnd events through the Coodra MCP hook tool, lifecycle_event. Sync-daemon stays asleep in solo mode.

terminal · launch

# → mcp-server   listening on 127.0.0.1:3100
# → web-v2       http://localhost:3001

# Confirm everything's alive

coodra doctor          # 12 essential checks (36 with --full)

Open the agent & watch.

Run coodra agent add <agent> or coodra agent repair <agent>, then launch your agent in the repo. SessionStart reaches Coodra through the plugin, opens a runs row, captures base_sha, and returns a compact manifest of recipes, decisions, context, and project state. The agent pulls bodies through MCP when needed.

Visit http://localhost:3001/runs to watch the trace populate live.

/03 — Deployment

Two modes. Same primitives.

Mode is a COODRA_MODE
env flag

Solo and Team mode share schema, code, and CLI. The difference is who sees what, and whether the sync-daemon boots.

/ solo · default

Everything on your laptop.

SQLite at ~/.coodra/data.db. Loopback only. Solo-bypass auth — no Clerk, no JWT, just SOLO_ACTOR stamped on every write. The sync-daemon does not boot. Zero network egress.

Best for: individual contributors, OSS hacking, air-gapped envs, contractors with a strict no-cloud policy.

Set: COODRA_MODE=solo
/ team · opt-in

Cloud-synced memory.

Same local SQLite — plus a Postgres + pgvector mirror you operate, plus Clerk for identity. The sync-daemon pushes sync_to_cloud outbox rows and pulls teammates' runs, decisions, and packs back into local SQLite.

Best for: small teams sharing context, multi-laptop developers, BYO-cloud self-host.

Set: COODRA_MODE=team · DATABASE_URL · CLERK_*

session
An agent-side identifier. One per IDE/agent invocation. Coodra never invents one — it accepts whatever the agent sends. UNIQUE (project_id, session_id) in runs
run
A row in the runs table — agent type, mode, status, base_sha, created_by_user_id, project_id. Bound to a session by get_run_id; reused across get_run_id calls within the same session. One run per session per project
lifecycle event
A normalized event from a native agent plugin: SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostCompact, Stop, or SessionEnd. Events resolve runs, refresh context, check policy, record activity, and finalize evidence.
hook MCP tool
lifecycle_event. The Coodra MCP tool native plugins call for lifecycle events. It is the developer entrypoint for run creation, prompt-time memory refresh, tool policy checks, event recording, compaction bookkeeping, and SessionEnd finalization.
memory
DB-backed, MCP-mediated project knowledge: Context Packs, Decisions, Work Pack links, wiki pages, recipes, manifests, policy teaching, and access telemetry. Coodra records explicit SessionStart manifest and policy-reason push rows, plus pull rows when the agent retrieves memory through instrumented MCP tools.
context pack
A durable markdown summary of one run: what changed, what was tested, what remains open, and what a future agent should know. Stored in context_packs, linked to runs and optionally Work Packs, searchable by MCP, and created by the agent or by SessionEnd lifecycle fallback.
work pack
An issue-bound implementation record under .coodra/work-packs/<slug>/ and the work_packs tables. Work Packs connect external work items from Jira, Linear-style planning tools, GitHub/GitLab, or manual sources to local plan/status, runs, decisions, and Context Packs.
agent recipe
Reusable task guidance, authored by humans or agents in .coodra/recipes/<slug>/. Pulled on demand via list_recipes / get_recipe when a task matches a recipe's trigger — not auto-injected.
decision
A structured architectural choice — description, rationale, alternatives, reversibility — recorded by the agent mid-run. Idempotent on sha256(description)[:32]. Surfaced to later sessions through lifecycle relevance refresh
code graph
The Graphify structural graph managed under .coodra/graphify/out/: graph.json, GRAPH_REPORT.md, and graph.html. It is queried through a separate Graphify MCP server and used for file-neighborhood context, wiki planning, and graph-backed decision lookup.
deep wiki
A two-pass architecture wiki. coodra wiki build creates grounding from source, Graphify, and prior Coodra memory; an agent saves structure and pages through wiki_save_structure / wiki_save_page; wiki_ask retrieves authored pages for future work.
policy
The pre-tool governance layer: kill switches, rules, grants, native advisory projections, path matching, just-in-time decision teaching, and fail-open behavior. If Coodra has no matching rule, it records audit context and leaves authority with the agent's native permission system.
policy decision
An append-only audit row: who asked, what tool, what input, what verdict. Idempotency key pd:{sessionId}:{toolUseId}:{toolName}:{eventType}. ADR-007

/04.1Runs & sessions

A session is what the agent calls itself. A run is what Coodra calls that work. The first call to get_run_id for a session either opens a new runs row, or — if the agent crashed and restarted — finds and resumes the existing one.

session → run binding
// MCP tool: get_run_id  ·  apps/mcp-server/src/tools/get-run-id/
const { runId } = await mcp.call("get_run_id", {
  sessionId: "cc-sess-2026-05-16-8a3f2c",
  projectSlug: "my-app",
  agentType: "claude_code",
});

// First call:  inserts a runs row, returns runId.
// Repeat call: returns the same runId (UNIQUE on project_id, session_id).

Every run_events row, every policy_decisions row, and the eventual context_packs row hang off this runId. run_events.run_id uses ON DELETE SET NULL so PreToolUse events that fire before the run exists still land — they just attach later when the row appears.

/04.2Lifecycle events

Lifecycle events are not user-facing commands. They are the machine-readable contract between a native agent plugin and Coodra's MCP server.

Event Primary Coodra behavior Developer mental model
SessionStartOpen or resume a run, capture base_sha, return session contract and memory manifest.Boot context.
UserPromptSubmitPerform bounded relevance refresh using prompt, file, Work Pack, FTS/BM25, and Graphify signals.Just-in-time context.
PreToolUseEvaluate kill switches and policy rules, then write policy_decisions.Govern before action.
PostToolUseRecord the event, external MCP activity, latency/error metadata, and pull-side memory access where applicable.Evidence after action.
PostCompactAdvance baseline generation; later prompt-time context belongs to the new generation.Keep post-compaction pull-through attribution honest.

The implementation center is apps/mcp-server/src/tools/lifecycle-event/handler.ts, with reusable finalization and memory workers in packages/lifecycle/. The important boundary is that the plugin reports events; Coodra normalizes, records, and answers through MCP.

Coodra memory exists to make future agent sessions start with project history, architectural intent, and task evidence without stuffing the whole past into every prompt.

Purpose

Continuity, not prompt stuffing

Memory gives the next agent the project state it cannot infer from the current prompt: what happened, why decisions exist, which issue is active, what files are implicated, and where the deeper explanation lives.

Storage

DB-backed and MCP-mediated

Solo mode writes to ~/.coodra/data.db. Team mode keeps the same local hot path and syncs to operator-owned Postgres. Agents read and write through MCP tools, not by mutating markdown mirrors directly.

Measure

Usefulness is observable

Coodra records two push channels today — session_start_manifest and policy_reason — plus pull rows from instrumented retrieval tools. Pull-through, stale-at-access share, bytes, latency, and actor breakdowns show whether memory helped or merely existed.

Memory surface How it is saved How it is retrieved What it is for
Context Packssave_context_pack or SessionEnd fallback.search_packs_nl, list_context_packs, read_context_pack.Resume what changed, what was tested, and what remains open.

At session start, Coodra can surface a compact manifest and bounded recent context, and that manifest is recorded as session_start_manifest push rows. On prompt submit, it performs a narrower relevance refresh using exact issue/file signals, Work Pack hints, FTS/BM25, and Graphify-backed file-decision lookup; that context is surfaced to the agent, but it does not currently create push rows. The agent then pulls full bodies only when useful, and pull access is recorded from instrumented tool outputs rather than guessed from the prompt.

Freshness is layered on top of memory instead of rewriting it. Gardening can mark a pack or decision stale, unverified, or fresh and can propose repairs, but it does not invisibly edit the historical record. That keeps Coodra useful as both memory and audit trail.

/04.4Work Packs

A Work Pack is Coodra's local, evidence-backed representation of a unit of implementation work. It can mirror Jira, Linear-style planning tools, GitHub/GitLab PRs, or a manual task, but provider reads and writes stay in the provider's own native MCP.

Scope

Issue-bound work state

Lives in .coodra/work-packs/<slug>/ and work_packs. It carries normalized Coodra type/status, provider-native issue type/status, local spec, implementation notes, sync notes, relationships, and metadata.

Provider

Native MCP handoff

The agent fetches fresh Jira or Linear-style planning data through that provider's MCP, then calls work_pack_upsert to persist the local map. Coodra stores provider keys and evidence; it does not own provider credentials.

Resume

Context with evidence

work_pack_status returns local Work Pack state for the agent, while Context Packs and Decisions linked to the same pack show what changed, why, and what remains open.

Moment Agent action Coodra record
ImportRead Jira, Linear-style, GitHub/GitLab, or manual task details through the relevant MCP or local source.external_work_items, work_packs, work_pack_external_links.
PlanWrite implementation notes, relationships, and normalized type/status through work_pack_upsert.spec_markdown, implementation_markdown, sync_markdown, relationship rows.
WorkSave Context Packs and Decisions with Work Pack slugs attached.work_pack_context_pack_links, work_pack_decision_links, latest activity rollup.
RefreshFetch fresh provider state through the provider MCP, then persist updated local state.sync_events, provider status fields, local_ahead / local_only sync state.
ResumeCall work_pack_status, then pull linked packs/decisions/context bodies only when needed.Local resume surface plus memory pull-through telemetry where instrumented memory tools are used.
Rule

Provider MCPs are the authority for external systems. Coodra is the local execution memory: it remembers what the agent understood, what it changed, which evidence is linked, and what should be resumed next.

/04.5Recipes & Context Packs

These three are easy to confuse because all three help an agent continue work. They differ by ownership and time: recipes guide before work, Work Packs scope issue-bound work, and Context Packs preserve after-work evidence.

→ before

Agent Recipe

Human- or agent-authored. Lives in .coodra/recipes/<slug>/. Reusable guidance the agent pulls on demand via list_recipes / get_recipe when a task matches its trigger.

Direction: human → agent.

↔ during

Work Pack

Issue-bound implementation state. Lives in .coodra/work-packs/<slug>/ and work_packs, with links to runs, decisions, Context Packs, relationships, and external work items fetched through Jira, Linear-style, GitHub/GitLab, or manual workflows.

Direction: issue ↔ agent ↔ evidence.

← after

Context Pack

Agent-authored (or lifecycle fallback on session end). One row per run in context_packs with title, content, content_excerpt, meta. Queryable cross-session via search_packs_nl, list_context_packs, read_context_pack.

Direction: agent → future agents.

Memory

Coodra memory is not a prompt dump. SessionStart can surface a compact manifest; the agent then pulls bodies through instrumented tools such as read_context_pack, search_packs_nl, list_context_packs, query_decisions, query_decisions_by_file, wiki_ask, list_recipes, and get_recipe. Work Pack state is retrieved through work_pack_status, but that tool is a resume surface rather than a pull-through telemetry source today.

If a saved pack has source: 'agent' and a new save_context_pack call arrives with the same runId, the response is status: 'idempotent_hit'. Automatically generated packs can be upgraded in place when the agent later provides richer context for the same run.

Sync

Work Packs are provider-neutral on purpose. Coodra does not own Jira or Linear credentials and does not call those APIs directly; the coding agent uses the relevant native MCP to fetch or update the planning tool, then calls Coodra's Work Pack tools to persist the local implementation map and evidence links.

/04.6Code graph & Deep Wiki

Graphify and Deep Wiki are connected, but they are not the same artifact. Graphify maps structure; the wiki explains it.

Graphify

Structural code graph

Coodra manages Graphify output at .coodra/graphify/out/. The current graph provides graph.json, GRAPH_REPORT.md, and graph.html; native plugins wire a separate Graphify MCP server beside Coodra MCP.

Deep Wiki

Grounded architecture docs

coodra wiki build creates grounding.md and job.md from source, Graphify communities, god nodes, and prior recorded work. Pages are saved through MCP and mirrored under .coodra/wiki/<slug>/md/.

For developers, the practical rule is simple: use Graphify when you need structural neighborhoods or dependency paths; use Deep Wiki when you need a human-readable explanation of the subsystem. wiki_ask retrieves authored wiki pages, while Graphify MCP answers graph questions directly.

/04.7Decisions

An ADR-grade record the agent emits when it makes a non-trivial choice: pick an ORM, change a public API shape, defer a refactor. They survive across sessions and surface to the next agent via the UserPromptSubmit event.

MCP tool · record_decision
await mcp.call("record_decision", {
  runId,
  description:   "Use better-sqlite3 instead of sql.js for primary store",
  rationale:     "Synchronous API matches MCP request lifecycle; ~3x faster on writes.",
  alternatives:  ["sql.js", "libsql/Turso"],
  confidence:    "high",
  reversible:    false,
});
// Idempotent on  dec:{runId}:{sha256(description)[:32]}
// Resurfaces on next  UserPromptSubmit  through lifecycle_event relevance refresh

/04.8Policy & kill switches

Two layers of guardrail. Kill switches sit above policy — they're operator-level pauses, evaluated first.

/01
kill_switch_check
Polymorphic (scope, target) — global, project, tool, agent_type. 5s in-process cache. Soft-resume keeps the row.
FIRST
/02
policy.check(event)
Cache-first DB read inside a Cockatiel timeout(100ms) + circuitBreaker(5) fuse. Picomatch path globs. First match wins by priority ASC.
EVALUATE
/03
recordPolicyDecision
Writes to policy_decisions with ON CONFLICT (idempotency_key) DO NOTHING. Async; the hook returns before the write.
AUDIT
/04
return verdict
ALLOW · ASK · DENY — only an explicit rule match returns DENY.
VERDICT
/--
FAIL_OPEN
On breaker open · isolation · timeout · any thrown DB error, returns { decision: 'allow', reason: 'policy_check_unavailable' }.
SAFETY NET

Policy rules match on five axes — event type, tool name, path glob, agent type, and priority. Decisions are append-only. The default policy seed lives in packages/db/src/ensure-default-policy.ts.

/06.3Sync & multi-tenancy

In team mode, the sync-daemon pushes outbox rows to cloud Postgres and pulls teammates' rows back into local SQLite — both directions on a 1-second tick.

LOCAL → CLOUD

team-rows-puller
Pulls runs · decisions · context_packs · run_events cloud → local via ON CONFLICT DO NOTHING. Skips __global__ + __solo__.
CLOUD → LOCAL
pull

Propagates org-scoped pauses to every teammate so a hard stop is global.
CLOUD → LOCAL

Every shared table carries Clerk user attribution: created_by_user_id on runs, decisions, context_packs, policies; paused_by_user_id / resumed_by_user_id on kill_switches. Web-v2 enforces single-tenant via COODRA_EXPECTED_ORG_ID — a deployment refuses to boot without it.

/11 — Operate

When things break.

First, run
coodra doctor

Every problem in Coodra leaves a trail in ~/.coodra/logs/, in policy_decisions, or in the doctor output. Start there.

/ symptom

Agent never sees Coodra context

SessionStart is not reaching Coodra's MCP lifecycle path. Confirm the native plugin is installed and healthy:

coodra agents reports the target agent fully wired?
coodra status shows mcp-server healthy on 3100?
tail ~/.coodra/logs/mcp-server.log shows native_plugin_lifecycle_event?

/ symptom

Policy denies something it shouldn't

Look up the audit row by idempotency_key = pd:{sessionId}:{toolUseId}:{toolName}:{eventType}. The matched_rule_id tells you exactly which rule fired.

If reason: 'policy_check_unavailable' — the engine fail-opened, never a deny. Check the breaker state in logs.

/ symptom

Sync-daemon can't connect

Symptoms: queue depth climbs in doctor (check 26), nothing appears on teammates' laptops.

Confirm DATABASE_URL reachable from this machine. coodra doctor --full runs cloud-reachability check 24. Look at ~/.coodra/logs/sync-daemon.log for connection errors. Restart with coodra stop --service sync-daemon && coodra start.

/ symptom

web-v2 refuses to boot

Almost always COODRA_EXPECTED_ORG_ID missing in team mode. The middleware refuses to start without it — by design, to prevent any Clerk-authed account in this deployment's Clerk app from reading your team's data.

If set but you land on /forbidden?reason=org_mismatch — your Clerk session is in a different org. Sign out and back in, or run coodra org switch <slug>.

/ symptom

SQLite locked or corrupted

Stop all daemons, snapshot the file, repair:

coodra stop && coodra db backup
sqlite3 ~/.coodra/data.db "PRAGMA integrity_check;"
coodra db restore <snapshot> if needed.

Open an issue with the doctor JSON + log tail.

/ symptom

No run_diff for completed run

query_run_diff returns analysis_pending, no_base_sha, or git_diff_failed. Common cause: the agent operated outside a git repo, or base_sha was unreachable when SessionEnd fired.

Re-trigger with coodra run show <id> --regen-diff after checking out the right commit.

/ symptom

Graphify or wiki context is stale

Check the managed graph first: coodra graphify status. Current managed output lives under .coodra/graphify/out/, not root-level graphify-out/.

Rebuild structurally without LLM spend via coodra graphify build --no-llm, then refresh the wiki with coodra wiki build and the two-pass wiki save flow.

/13 — Contribute

Contribution guide.

MIT licensed
PRs welcome

Coodra is built linearly, start to finish, as a production-grade system. Contributions are welcome — and held to the same bar.

/13.1Core principles (read first)

  1. Ship complete or don't merge. No placeholder surfaces, no mocked endpoints to make the UI render, no "we'll come back to this later." Every module ships end-to-end.
  2. Local-first remains the default. Any new feature must work offline. If it requires the cloud, it must degrade gracefully back to local + offer a clear path to enable.
  3. Fail-open in the hot path. Hooks return ALLOW on engine fault. Hot-path code paths catch and log async — never throw at the agent.
  4. Append-only audit. Don't add an UPDATE on policy_decisions, decisions, or run_events. Resurface via a new row with the same idempotency key.
  5. Document divergence. If your PR contradicts an ADR, README claim, or essentials doc — update the source-of-truth doc in the same commit.

/13.2Workflow

/01

Pick or file the issue.

Look for good-first-issue or help-wanted. For non-trivial work, open an issue first so we can align on shape before code lands.

/02

Branch off main.

Naming: feat/<short-slug>, fix/<short-slug>, chore/<short-slug>, docs/<short-slug>. Squash-merge expected at the end.

/03

Write the tests.

Unit tests live next to source as *.test.ts. New tables/migrations require a schema-parity test. New MCP tools require a happy-path + soft-failure test at minimum.

/04

Update docs.

If you touched the public surface — env vars, CLI flags, MCP tools, lifecycle payloads — update the relevant table in this docs page in the same PR. If the change alters durable architecture, record or supersede the decision through record_decision.

/05

Pre-commit & push.

The .githooks/pre-commit hook runs the migration-lock check automatically when packages/db/* is staged. Before pushing: pnpm lint:fix && pnpm typecheck && pnpm test:unit.

/06

Open the PR.

Title in conventional-commit form (feat:, fix:, chore:, docs:). Body should state: what changed, why, how to verify locally, and any decision/docs it touches. CI will run verify, integration, hook-adapter-smoke, windows-core-smoke, windows-native-full-smoke, and e2e.

/14 — Design

Decisions of record.

Coodra decisions store
curated highlights

Architectural decisions are durable Coodra memory, written through record_decision and superseded through decision edges rather than maintained as standalone ADR files. The cards below are curated highlights of the most load-bearing decisions.

ADR-007

Append-only audit

Policy decisions, decisions records, and kill-switch state changes are append-only. Idempotency keys gate writes. Resumes don't delete — they stamp resumed_at on the existing row. Recovery and forensics become trivial.

ADR-010

Graphify is a reader

Coodra consumes Graphify as a separate managed MCP server pointed at .coodra/graphify/out/graph.json. It installs and refreshes the structural graph, but does not fold graph queries into Coodra's own tool list or mint Work Packs from graph communities.

ADR-012

Agent-driven NL assembly

Natural-language memory assembly stays inside the agent loop. Coodra exposes retrieval tools (search_packs_nl, list_context_packs, read_context_pack); the agent ranks, synthesizes, and cites returned evidence.

ADR-013

Run Diff in process

Shared lifecycle finalization captures base_sha → head_sha, stores deterministic git diff evidence, and links the result back to the run without depending on a separate analysis service.

ADR-014

Tier 2.5 RBAC

Three roles — viewer, member, admin — parsed from Clerk org roles. assertCanEdit centralises the gate; ownership unlocks member-level edits on rows they created. Knowledge mutations are their own narrower gate.

COOD-53

Lifecycle is MCP-native

Native plugins route session events to lifecycle_event. Shared @coodra/lifecycle owns finalization, diff capture, auto Context Packs, Work Pack updates, and graph refresh.

/16 — Help

Frequently asked.

Short answers
linked deep dives
Is Coodra a code editor?
No. It runs alongside your editor or coding agent. Coodra is the plugin/MCP layer between the agent and your project: context in, evidence out.
Does it call out to OpenAI / Anthropic?
Coodra itself does not call model APIs. Your agent talks to its model. Coodra talks to the agent through MCP and may run key-free structural Graphify refreshes locally.
Is Graphify part of Coodra?
No. Graphify is an independent open-source project. Coodra manages the local wiring, MCP entry, and .coodra/graphify/out/ artifact path; Graphify owns the graph engine. See the repository NOTICE file for attribution.
Can I use Coodra without Claude Code?
Yes. Codex, Cursor, Devin, and Antigravity are supported through native plugins, and any MCP-speaking client can talk to mcp-server.
What happens if Coodra's lifecycle path goes down?
The agent keeps coding through its native flow. You lose Coodra audit, memory refresh, run diffs, and policy advice for affected events until MCP/plugin health is restored.
Where is my data stored?
In solo mode: only at ~/.coodra/data.db. In team mode: also in the Postgres you operate. Coodra ships no hosted backend.
Can I delete my run history?
Yes — scripts/wipe-disposable-projects.sh or scripts/wipe-all.sh. Append-only doesn't mean undeletable; it means we don't update rows in place.
Can I change the web port?
Yes. Set COODRA_WEB_PORT for Coodra's service manager, or PORT when running the Next.js standalone process directly. Default is 3001.
Is the web UI required?
No — it's a convenience. coodra start --no-web skips it. coodra ui gives you a TUI alternative.
